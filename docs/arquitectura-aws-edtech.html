02 · Responsabilidad por capa

Para qué sirve cada pieza

Así se entiende por qué la arquitectura tiene varias cajas y cuáles conviene revisar primero para bajar la factura.

Entrada y contenido

API GatewayALBS3CloudFront / WAF

API Gateway publica HTTPS y puede aplicar controles de API. ALB reparte solicitudes entre servicios ECS y enruta por path. S3 guarda estáticos y medios. CloudFront serviría contenido en el borde; en este entorno está apagado.

Aplicación y pagos

ECS FargateECRCognito

Web Next.js SSR, identity, catálogo, matrícula, gamificación, flashcards, pagos, afiliados, servicio IoT y terminal virtual. ECR conserva las imágenes. Cognito administra identidad de usuarios. Los servicios están aplicados, con desired/running en cero.

Datos y eventos

Aurora PostgreSQLEventBridgeSQS + DLQ

Aurora persiste cursos, órdenes y comisiones; EventBridge y SQS desacoplan los eventos entre dominios y permiten reintentos. Aurora puede pausar el cómputo; almacenamiento, respaldos y otros recursos siguen siendo persistentes.

Terminal IoT

IoT CoreThing / ShadowRule → SQS

El terminal virtual consulta su configuración, reporta estado y recibe avisos. IoT Core enruta telemetría a una cola por una regla. Thing y Shadow están creados, pero la regla está deshabilitada y el simulador ECS está detenido.

Seguridad

IAMKMSSecrets ManagerVPC

Roles temporales por servicio, secretos externos, claves de cifrado y security groups. IAM no tiene cobro por usuario/rol, pero las claves KMS creadas por el cliente y los secretos guardados sí pueden mantener un coste mensual.

Operación y despliegue

CloudWatchTerraform state S3DynamoDB lock

Logs con retención corta ayudan a diagnosticar; Terraform conserva estado remoto versionado y bloqueos. Revisar retención, versiones antiguas, snapshots, ECR y secretos evita “costos zombie” aun con aplicaciones apagadas.

03 · Decisión de borde

¿API Gateway reemplaza al ALB?

Depende de dónde termina el tráfico. API Gateway administra APIs; ALB distribuye tráfico entre destinos de aplicación. Se superponen en algunas funciones, pero no son un reemplazo directo en todas las arquitecturas.

Hoy en el código

API Gateway → ALB → ECS

La HTTP API actual recibe HTTPS y hace proxy hacia el ALB, donde viven las reglas por ruta. AWS confirmó la integración HTTP_PROXY al DNS del ALB retirado. Si se restaura ese ALB, no hace falta cambiar la app para esa topología.

API Gateway existeALB no existe

El endpoint público detectado es https://7if9q98464.execute-api.us-east-1.amazonaws.com; su integración apunta a edtech-dev-alb-253365714.us-east-1.elb.amazonaws.com, que fue retirado.

Mantener contenedores

API Gateway → VPC Link → Cloud Map/ECS

HTTP API puede integrar en privado con un servicio ECS registrado en Cloud Map. Eso permite quitar ALB y enrutar a tareas por descubrimiento. Requiere crear VPC Link, service discovery y revisar registros SRV/Service Connect, health y permisos.

Ventaja: mantiene ECS y evita el cargo del ALB. Trade-off: VPC Link/ENI y Fargate mientras ejecuta siguen costando; tampoco resuelve la salida a AWS APIs desde las subredes privadas.

Menor coste ocioso

API Gateway → Lambda

HTTP API puede llamar Lambda directamente sin ALB ni VPC Link. Para tráfico esporádico, API Gateway y Lambda cobran principalmente por invocaciones/duración; la capa de entrada no queda cobrando por hora como un ALB encendido.

Trade-off: no es cambiar una casilla: hay que adaptar los controladores/servicios al modelo Lambda y resolver acceso a Aurora, límites de conexión y el frontend Next SSR.

Mi recomendación: no cambiar ALB por API Gateway en Terraform hasta elegir el modelo de cómputo. Para conservar estos microservicios ECS, evaluar HTTP API + VPC Link + Cloud Map y calcular el coste de enlace/horas. Si el requisito principal es demo ocasional y presupuesto muy bajo, diseñar una porción serverless API Gateway + Lambda, dejando claro que requiere adaptar la aplicación. La mejor opción depende de cuánto queremos refactorizar.
API Gateway no sustituye NAT. NAT resuelve salida de tareas privadas hacia servicios/endpoints públicos; ALB resuelve distribución de solicitudes entrantes. Si se quita el NAT, hay que diseñar egress separado para que Fargate tire de ECR, lea secretos, escriba logs y llegue a IoT/SQS. API Gateway solo cubre el camino de entrada a la API.

05 · Camino sugerido

Separar arquitectura de producción y modo de demostración

La arquitectura completa enseña microservicios, mensajería e IoT; puede quedarse como referencia aplicada en pausa. La demo debe activar sólo las piezas necesarias durante un tiempo controlado.

Camino A · Continuar con ECS

Conservar los 10 contenedores y sus límites por servicio; usar API Gateway + VPC Link/Cloud Map o recuperar ALB sólo para la ventana de prueba. Diseñar por separado una salida para ECR, Secrets Manager, CloudWatch, SQS e IoT.

Elige esto si: el objetivo es demostrar los microservicios y la integración cloud tal como fueron construidos. Implica medir Fargate y red por hora y retirar recursos de cobro horario al terminar.

Camino B · Recortar para bajo tráfico

Mover rutas HTTP de bajo uso a Lambda detrás de API Gateway HTTP, y consumidores/eventos a Lambda + SQS/EventBridge. Mantener Aurora mientras el modelo relacional aporte valor o evaluar una tabla DynamoDB en una fase aparte. El terminal IoT puede seguir siendo virtual.

Elige esto si: prima gastar sólo durante la demo. Requiere trabajo de adaptación y no se resuelve reemplazando ALB con un toggle.

Secuencia segura para continuar: 1) obtener un corte actualizado en Cost Explorer para identificar gastos persistentes; 2) decidir entre mantener ECS o diseñar el slice serverless; 3) actualizar Terraform y comprobar el plan; 4) hacer una prueba breve del QR, venta, comisión e IoT; 5) volver a aplicar modo pausado y revisar la factura después de su demora de contabilización.

06 · Estado y esfuerzo de migración

Qué cambia para pasar a un backend bajo demanda

Evaluación del código y Terraform del repositorio, contrastados con el último inventario AWS disponible (11 oct 2026). Es un análisis local; antes de retirar recursos hay que confirmar el estado y la factura actuales en la cuenta.

Conclusión: retirar ALB y Fargate es sencillo como decisión de arquitectura, pero migrar los diez servicios no es un cambio de Terraform. La complejidad está en convertir APIs Express, workers que hoy viven en procesos permanentes y acceso a PostgreSQL. Para la demo recomiendo migrar primero el flujo QR → visita → compra simulada → comisión y dejar el resto pausado.
Estado actual

Diez servicios ECS/Fargate preparados, cero tareas activas

Web Next.js SSR y nueve servicios adicionales: identity-access, catalog, enrollment-progress, gamification, flashcards, payments, affiliates, iot-terminals y terminal-simulator. Los módulos ECS declaran tareas de 0,5 vCPU y 1 GB; todos tienen desired count 0 en el entorno revisado.

Cada servicio tiene su propio directorio de infraestructura/estado Terraform. Las APIs usan Express y Drizzle sobre PostgreSQL/Aurora. La API Gateway HTTP existente conserva una integración HTTP_PROXY hacia el DNS del ALB retirado, por lo que el endpoint no llega a esos servicios.

Destino propuesto

Web y funciones sin contenedores siempre encendidos

Amplify aloja la web Next.js; API Gateway HTTP enruta las llamadas a funciones Lambda. IoT Core invoca Lambda desde una regla. DynamoDB puede guardar atribución y comisiones del demo, o se conserva Aurora al principio si evitar migración de datos tiene más valor.

Ya no hay ALB, VPC Link ni NAT para ese flujo. La modularidad se conserva en el código; no es necesario mantener diez servicios ECS desplegados para presentarla.
