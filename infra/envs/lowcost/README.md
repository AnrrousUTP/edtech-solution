# Entorno serverless lowcost

## Estado de implementación

Esta carpeta administra la infraestructura serverless aislada del entorno anterior. La migración objetivo cubre los ocho dominios del producto: `identity-access`, `catalog`, `enrollment-progress`, `gamification`, `flashcards`, `payments`, `affiliates` e `iot-terminals`, además de `control`. La web usa Next.js en Amplify, las APIs usan API Gateway/Lambda y Cognito conserva la identidad y el rol único de cada cuenta. Las capacidades quedan apagadas hasta que se autorice el corte.

La configuración predeterminada conserva el modo pausado y prepara los ocho dominios para la arquitectura objetivo. Terraform no se ha aplicado. Aplicar la base puede generar cargos por almacenamiento de tablas/bucket aunque no haya tráfico; no aplicar Terraform mientras AWS deba permanecer apagado. `terraform fmt -check` es local. Para validar sin backend usa un `TF_DATA_DIR` temporal nuevo, `init -backend=false -lockfile=readonly` y luego `validate`: pasó en lowcost y Cognito dev. El `.terraform` existente apuntaba a la clave antigua `lowcost/affiliate-iot` y devolvió 403; no reutilizar esa metadata para validar. Esta validación no crea un plan ni verifica una publicación. No ejecutar `plan` ni `apply` durante la pausa. `enabled_domains` limita explícitamente los dominios incluidos si la configuración futura lo requiere.

La API de contenido exige rol `estudiante` y una matrícula activa no vencida. Catalog consulta a Enrollment mediante una invocación Lambda privada permitida solo por IAM; si no puede validar el acceso, responde sin entregar la lección.

Cada Lambda de dominio accede solo a su tabla DynamoDB y sus índices; la tabla `control` queda para la web cuando se habilite IA. Las políticas S3 se limitan al prefijo y a las acciones que usa cada dominio: Catalog escribe `catalog/lecciones/*`, Flashcards lee ese prefijo y Gamification lee/escribe `certificados/*`. Los demás dominios no reciben permisos S3 de contenido. Los servicios escriben eventos en el outbox DynamoDB; solo la Lambda publicadora necesita `events:PutEvents`.

La ruta HTTP interna de respuestas del catálogo rechaza tokens ausentes o vacíos. El destino Lambda usa invocaciones IAM entre dominios para validar matrícula y consultar respuestas; no necesita exponer esa ruta entre servicios.

## Inicio con destino vacío

La pérdida de los datos actuales está aceptada. No exportar Aurora ni ejecutar la carga de `LegacySnapshotRecord`. DynamoDB inicia vacío y el catálogo productivo lo crea el docente después del corte. `tools/seed/lowcost-affiliate-demo.ts` contiene datos sintéticos opcionales para validar afiliación: cursos de muestra, precios y proyecciones de aprendizaje; no carga usuarios, matrículas, órdenes ni comisiones. Su modo `plan` solo imprime valores y `apply` escribe en AWS, por lo que este último queda prohibido mientras AWS siga apagado.

Las herramientas `db:migrate:aurora-dynamodb` quedan fuera de este corte y no se deben ejecutar para esta migración. La cola `identity_events` consume altas Cognito y eventos de nivel de inscripción. `infra/envs/dev/cognito` ya toma su URL y ARN del estado `lowcost/serverless`; su precondición impide aplicar Cognito hasta que la cola destino esté creada y expuesta en outputs. Por eso se activa primero el backend lowcost y luego se actualiza Cognito, sin dejar registros nuevos en la cola del entorno antiguo.

Los paquetes se generan en Linux con `bun run lambda:build <dominio>` o, desde Windows, con `bash tools/lambda/build-linux-container.sh <dominio>` en WSL. Los dominios preparados y `outbox` producen `.local/lambda/<dominio>/<dominio>.zip` con `handler.mjs`, esquemas y manifiesto hash/revisión. Antes de publicarlos requieren smoke tests locales; la integración de AWS queda para después de la pausa.

El primer corte mantiene paridad de funciones acordadas; no transfiere filas existentes. Cualquier seed sintético se ejecuta por separado y solo para validación; los datos productivos iniciales los crea el docente. Los datos nuevos deben escribirse con claves operativas PK/SK y proyecciones consultables por los handlers, sin sobres de legado.

Este estado es independiente de `infra/envs/dev`. No importa el estado anterior ni contiene recursos ECS, ALB, NAT, Aurora o KMS administrados por el cliente. No ejecutar `apply` hasta revisar el plan, haber publicado artefactos Lambda válidos y configurar los valores de `terraform.tfvars` fuera de Git.

La configuración predeterminada deja `pause_public_services=true`, `ready_api_domains=[]`, `enable_event_consumers=false`, `enable_outbox_publisher=false`, `event_consumers_release_ready=false`, `enable_affiliate_events=false`, `enable_iot=false`, `enable_ai=false` y `operation_mode=pausado`. Una API requiere simultáneamente el modo público y su dominio en `ready_api_domains`; no se crean rutas para los demás dominios. Cognito exige issuer y JWKS HTTPS. Los consumidores SQS por dominio requieren `enable_event_consumers=true` y `event_consumers_release_ready=true`; el publicador outbox puede habilitarse por separado con `enable_outbox_publisher=true` cuando sus dominios destino estén listos. Cada flujo usa su cola y DLQ de dominio; no hay una cola genérica que duplique todos los eventos. Las políticas de DLQ autorizan únicamente la regla EventBridge correspondiente y esperan a que esa política exista antes de crear el target. Al habilitar colas, CloudWatch alerta por cada DLQ y SNS notifica a `budget_notification_emails`; con el entorno pausado no se crean estos recursos. La expiración de órdenes invoca Payments directamente y la reconciliación programada invoca el publicador outbox. Las reglas de Payments → Affiliates e IoT permanecen apagadas con el entorno pausado. `budget_notification_emails` debe contener de uno a diez correos válidos antes de ejecutar un plan; Budgets exige al menos un suscriptor por alerta.

Payments usa PayPal real en la Lambda: crea una orden, devuelve al usuario a `/checkout/resultado`, captura el pago aprobado y confirma el resultado por webhook firmado. La cuenta debe preparar en Secrets Manager el secreto cuyo nombre define `paypal_secret_name` (predeterminado `edtech/lowcost/paypal`) con `PAYPAL_ENV`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID` y `MONEDA_DEFAULT`; no se guardan credenciales en Terraform. El ID del webhook debe corresponder al endpoint `/api/payments/webhook` del dominio de Amplify. Al habilitar Payments, Terraform crea la cola de webhooks y su DLQ, limita IAM a esa cola y a ese secreto, y agrega `URL_BASE` HTTPS a la Lambda. El sandbox debe validarse antes del corte; no se ha consultado ni modificado AWS.

El backend usa el bucket remoto ya existente, pero requiere una clave nueva. Inicialización sugerida, únicamente cuando el equipo autorice aprovisionar este estado:

```powershell
terraform -chdir=infra/envs/lowcost init -backend-config="bucket=edtech-tfstate-047600599757" -backend-config="key=lowcost/serverless/terraform.tfstate" -backend-config="region=us-east-1" -backend-config="dynamodb_table=edtech-tflock"
terraform -chdir=infra/envs/lowcost validate
terraform -chdir=infra/envs/lowcost plan -var-file="terraform.tfvars"
```

Antes de habilitar un dominio se debe subir su ZIP al bucket privado indicado por `lambda_artifact_bucket`, bajo `<lambda_artifact_prefix>/<dominio>.zip`. Los paquetes deben exponer `handler.handler`. Para habilitar la API de afiliados, provisionar el SecureString de `referral_signing_parameter_name`, rellenar las tres variables de Cognito y añadir `affiliates` a `ready_api_domains`. Su consumidor de eventos se activa por separado con `enable_affiliate_events=true`, una vez que pagos y catálogo publiquen en el bus low-cost. Para Amplify, la propietaria conecta el repositorio `AnrrousUTP/edtech-solution` desde la consola y conserva el plan Free. Luego se cargan `amplify_app_id`, `amplify_default_domain` y `cognito_domain` en `terraform.tfvars`; se importan la app y la rama ya creadas con `terraform -chdir=infra/envs/lowcost import 'aws_amplify_app.production[0]' <app-id>` y `terraform -chdir=infra/envs/lowcost import 'aws_amplify_branch.production[0]' <app-id>/main`. La configuración omite `access_token`: Amplify mantiene su conexión OAuth de consola fuera del estado Terraform. La rama recibe API, Cognito, modo IA/IoT y demás variables de runtime; `amplify.yml` las copia desde el entorno de build a `apps/web/.env.production`, como requiere Next.js SSR en monorepos. Con el modo pausado la compilación automática permanece apagada. El comando `plan` no cambia recursos AWS.

El app client de Cognito se gestiona fuera de este estado. Cuando Amplify tenga dominio definitivo, añadir `https://<rama>.<dominio>/api/auth/callback` a su allowlist de callbacks y `https://<rama>.<dominio>/` a la allowlist de logout en el estado que administra Cognito. Si se reutiliza el pool de este repositorio, el cliente lo administra `infra/envs/dev/cognito`; verificar el Hosted UI antes del corte.

## Aprovisionar un rol único

El alta pública solo concede `estudiante` o `afiliado`. Para cuentas operativas, `tools/aws/asignar-rol-cognito.mjs` resuelve el usuario por correo y mantiene un solo grupo de aplicación; conserva grupos Cognito ajenos a esos tres roles. El modo `plan` es predeterminado; `apply` exige `AWS_PROFILE=edtech`, el `COGNITO_POOL_ID` destino, confirmación del correo y la cuenta AWS del proyecto. Ejecutar estas operaciones solo cuando AWS se reactive.

Las tablas usan capacidad bajo demanda, claves compuestas `PK/SK`, índices secundarios dispersos `GSI1/GSI2`, cifrado de AWS y protección contra borrado. El seed sintético se valida contra su contrato y los flujos del producto; el catálogo productivo no se carga desde Aurora porque los datos históricos se descartan.

## Configuración del terminal IoT en Amplify

El navegador no recibe claves AWS permanentes. `/api/iot/session` valida la sesión y la propiedad del afiliado, asume el rol STS acotado al Thing `terminal-demo-01` y entrega una URL WSS SigV4 válida para el handshake. Terraform limita `Connect`, `Publish`, `Subscribe` y `Receive` a ese Thing, su Shadow `promotion` y los topics de `edtech/lowcost`. La regla IoT → SQS solo se crea cuando se habilitan explícitamente el modo público y `enable_iot`.

Después de conectar Amplify y conocer su rol SSR, pasar su nombre a `amplify_execution_role_name` para asignarlo a la app y permitirle asumir únicamente el rol IoT de sesión. Terraform coloca `APP_URL`, `API_BASE`, `EDTECH_IOT_ENABLED`, `EDTECH_IOT_DATA_ENDPOINT`, `EDTECH_IOT_SESSION_ROLE_ARN` y `EDTECH_IOT_THING_NAME` en la rama. El endpoint, el ARN y el nombre del Thing están disponibles como outputs Terraform. No establecer la variable IoT como habilitada hasta completar y probar los handlers y consumidores Lambda.
