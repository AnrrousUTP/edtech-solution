# DECISIONS.md

Registro de decisiones. Las D1-D20 vienen del plan (`plataforma_edtech/00-resumen.md`) y
no se renegocian. Las A-xx son supuestos tomados durante la ejecución por Fable, con su
motivo, tal como exige el doc 17 §0.4.

### F3 — identity-access

- **A-11** — `enrollment.curso-completado.v1` gana el campo **opcional** `nivelMax` (nivel máximo del curso). enrollment lo toma de su proyección de catálogo y identity lo usa para la regla `max(nivel, nivelMax)` del doc 02 §2. _Motivo:_ el payload del doc 05 §2.3 no traía el dato que identity necesita para subir el nivel; es un cambio compatible (campo opcional, doc 05 §8) y la opción preferida por D14: "que el evento traiga el dato".
- **A-12** — La Lambda post-confirmation **encola el alta directo en `sqs-identity`** (mensaje interno `identity.alta-usuario-cognito.v1`, que no viaja por el bus) en vez del PUT interno firmado con SigV4 del doc 08 §4. _Motivo:_ el propio doc 08 §4.1 define la cola como camino de resiliencia; hacerla camino único elimina la verificación SigV4 (superficie extra) y funciona aunque el servicio esté caído. La reconciliación y el alta perezosa siguen como redes.
- **A-13** — La Lambda pre-token **no** agrega el claim `nivel`; solo `mfa_pendiente` para admins sin MFA. _Motivo:_ el claim `nivel` exigiría acceso a la BD desde la Lambda; el doc 08 §3 lo declara "una optimización" y el dato autoritativo se sirve por `GET /api/identity/me`.
- **A-14** — Conexiones TLS a Aurora con `rejectUnauthorized: false` (cifradas, sin verificación de CA). _Motivo:_ la CA de RDS no viene en la imagen base; riesgo bajo en dev. Endurecer con `global-bundle.pem` queda como mejora anotada.
- **A-15** — Las imágenes Docker **no** hacen `bun build` (bundle): copian el código y Bun ejecuta TS directamente. _Motivo:_ el kernel carga los 26 schemas JSON en runtime desde `import.meta.dir`; el bundle rompería esas rutas sin aportar más que tamaño.
- **A-16** — App client `edtech-dev-pruebas` con `ADMIN_USER_PASSWORD_AUTH`, solo para verificación automatizada. _Motivo:_ el client web cumple el doc 08 §2 (solo code+PKCE); verificar tokens por guion exige un flujo sin navegador, y `admin-initiate-auth` requiere credenciales IAM del operador — no abre superficie pública.
- **A-17** — Los roles `svc_*` reciben `GRANT CREATE ON DATABASE edtech`. _Motivo:_ `CREATE SCHEMA IF NOT EXISTS` (que el migrador de Drizzle emite siempre) chequea el ACL de la base **antes** que la existencia del schema; sin el grant toda migración falla. Crear schemas nuevos no permite leer schemas ajenos: I-4 intacto y verificado tras el cambio.

### F4 — catalog

- **A-18** — El contenido de lecciones (`GET /api/catalog/lecciones/:id`) exige usuario autenticado pero **no** verifica matrícula: el gating de acceso pago vive en el flujo del player (enrollment decide qué mostrar). _Motivo:_ catalog no conoce matrículas (doc 02 §5.2) y verificar contra enrollment sería una llamada síncrona en el camino caliente (prohibida por D14). Endurecerlo (token de acceso firmado por matrícula o URLs firmadas) queda anotado como deuda.
- **A-19** — Segunda lectura síncrona documentada (además de la del doc 05 §7): **enrollment → catalog** `GET /api/catalog/interno/bancos/:id/respuestas`, con token compartido (`edtech/dev/interno` en AWS), para corregir evaluaciones y el test de nivelación. Cumple las tres condiciones: es lectura, ocurre solo al entregar un intento (no en cada página), y el consumidor la hace con timeout y degradación (el intento queda EN_CURSO y se reintenta). _Motivo:_ el payload de los eventos de catalog no transporta respuestas correctas y no existe evento de bancos; duplicarlas en una proyección de enrollment exigiría un evento nuevo con las respuestas viajando por el bus hacia todos los suscriptores del prefijo `catalog.` (incluida la cola de notificaciones), que es peor.
- **A-20** — `publicar` un curso emite además `catalog.contenido-actualizado.v1` por cada tomo. _Motivo:_ la regla `flashcards-desde-catalog` solo escucha contenido-actualizado; sin esto, el contenido publicado por primera vez jamás generaría mazos. La edición de contenido de un curso ya publicado emite el mismo evento (doc 05 §2.2).
- **A-21** — El seed (doc 03 §11) deja los cursos en `BORRADOR`; publicarlos es `tools/seed/publicar-cursos.ts` vía API de admin. _Motivo:_ los eventos de publicación no se pueden "sembrar" por SQL; publicar por la API emite los eventos reales y alimenta las proyecciones de enrollment/payments por el camino normal.

### F4-bis — primer despliegue real

- **A-22** — El listener del ALB de dev es **HTTP:80** (el doc 07 §5 pide 443). _Motivo:_ sin dominio propio no existe cert ACM validable; el HTTPS de cara al público lo pone CloudFront con su certificado por defecto (`*.cloudfront.net`) desde el módulo edge — imprescindible además para el webhook de PayPal (F8), que exige HTTPS. El tráfico CloudFront→ALB va por el origen HTTP dentro de AWS.
- **A-23** — La prioridad de listener rules por servicio queda fija: identity=10, catalog=20, enrollment=30, gamification=40, flashcards=50, payments=60. _Motivo:_ paths disjuntos; el número solo necesita ser estable y único.

### F5 — enrollment-progress

- **A-24** — Tercera lectura síncrona documentada: **enrollment → catalog** `GET /api/catalog/carreras` (API pública) para saber qué cursos compone cada carrera al completar uno, y así poder emitir `carrera-completada`. _Motivo:_ ningún evento del catálogo cerrado transporta la composición de carreras, y `enrollment` es el único que sabe qué cursos completó el estudiante. Cumple las tres condiciones del doc 05 §7: es lectura, ocurre solo al completar un curso (no en cada página) y degrada — si catalog no responde, el curso se completa igual y el evento de carrera se evalúa en el próximo cierre de curso. Verificado con un test que simula catalog caído.
- **A-25** — La tabla `enrollment.matriculas` gana `curso_completado_at`, y `cursos_proyeccion` gana `precio` y `nivel_max` (el doc 03 §6 no los tenía). _Motivo:_ `curso_completado_at` es lo que hace idempotente la emisión de `curso-completado` (sin él, cada lección recompletada lo reemitiría); `precio` decide si una matrícula GRATUITO es legítima sin llamar a catalog; `nivel_max` alimenta el campo A-11 del evento. Los tres llegan por eventos: siguen siendo proyección, no fuente de verdad.
- **A-26** — El test de nivelación usa umbral fijo 60 % por nivel (doc 02 §2) y no marca aprobado/reprobado; las evaluaciones de tomo usan el `umbral_aprobacion` del tomo, que viaja en la respuesta interna de catalog. _Motivo:_ el doc fija el 60 % para nivelación y el 70 % por defecto para tomos, pero el umbral real es por tomo y lo posee catalog.

### F6 — gamification

- **A-27** — El `nombre_titular` del certificado se congela con el **usuarioId** cuando gamification no conoce el nombre real. _Motivo:_ el nombre vive en `identity.usuarios` y ningún evento del catálogo cerrado lo transporta hasta gamification (`curso-completado` trae `cursoTitulo`, no el nombre del estudiante). Las opciones eran: (a) una cuarta lectura síncrona a identity en el momento de emitir —en el camino de un consumidor de eventos, peor que las tres ya documentadas—, (b) proyectar los nombres desde `identity.usuario-registrado.v1`, que sí llega a gamification. **(b) es la solución correcta y queda como deuda inmediata**: la proyección se agrega cuando el frontend muestre el certificado (F9), porque exige rellenar los perfiles ya creados. Mientras tanto el certificado es funcional y verificable; solo el nombre impreso es provisional.
- **A-28** — El PDF del certificado se genera **sin librería**: `PdfCertificadoGenerador` escribe un PDF 1.4 válido a mano (una página, Helvetica, texto centrado). _Motivo:_ las alternativas eran un navegador headless (cientos de MB en la imagen, y el doc 16 vigila el tamaño) o una librería de layout para una página de texto plano. El texto se normaliza a Latin-1 porque `WinAnsiEncoding` no cubre más, y un certificado con tildes rotas es peor que uno sin tildes. Si el certificado gana diseño gráfico, la decisión se revisa.
- **A-29** — El código de verificación usa el formato `EDT-XXXX-XXXX` con alfabeto sin caracteres ambiguos (sin 0/O, 1/I/L). _Motivo:_ el doc 03 §7 pide un código público único sin fijar formato; este se dicta por teléfono y se transcribe desde un PDF impreso sin confusiones.

### F7 — flashcards

- **A-30** — El mazo guarda `lecciones_fuente` (jsonb con las claves S3 del evento), campo que no está en el layout del doc 03 §8. _Motivo:_ el worker de generación corre **después** del evento, en otra cola: necesita saber qué contenido leer y el evento original ya no está disponible. Guarda la **referencia** (clave S3), nunca el contenido: la frontera del doc 02 §7.3 se mantiene.
- **A-31** — El mazo guarda también `intentos`, para el tope de 3 del doc 10 §7. _Motivo:_ el contador debe sobrevivir al reintento de SQS, que ocurre en otra invocación del worker; en memoria se perdería y el tope no existiría.
- **A-32** — Un fallo de generación con intentos disponibles deja el mazo en `GENERANDO` y devuelve `Ok`, para que SQS reintente por su cuenta al vencer el visibility timeout. Solo al tercer intento el mazo pasa a `FALLIDO` y emite `generacion-fallida`. _Motivo:_ devolver NACK haría que el mensaje contara reintentos por dos vías distintas (la del mazo y la de SQS) y llegaría a la DLQ antes de agotar los 3 intentos de negocio.
- **A-33** — El adaptador de Bedrock usa `InvokeAgent` del Agent Runtime, y el `modeloUsado` que se registra es el **declarado en configuración** (`BEDROCK_MODEL_ID`), no el que devuelve la respuesta. _Motivo:_ la respuesta del Agent Runtime no incluye el model ID; el valor autoritativo es el que Terraform resolvió por CLI en tiempo de build (D8) y pasó como variable de entorno. Se verifica contra el modelo real en F11.

### F8 — payments (hallazgos de infraestructura)

- **A-34** — **La cuenta no puede crear distribuciones de CloudFront**: `AccessDenied: Your account must be verified before you can add new CloudFront resources` (requiere abrir un caso con AWS Support). El webhook de PayPal exige HTTPS y el ALB de dev es HTTP (A-22), así que la terminación TLS del borde la da un **API Gateway HTTP API en modo proxy transparente** al ALB. _Motivo:_ es la sustitución más fiel del rol que CloudFront tenía aquí — dar HTTPS al borde y pasar headers y cuerpo crudo intactos, que es justo lo que la verificación de firma de PayPal necesita. **No contradice D10**: la entrada HTTP de los servicios sigue siendo el ALB con listener rules; el HTTP API no enruta por servicio, no tiene autorizadores ni planes de uso, y desaparece en cuanto CloudFront esté disponible. El CloudFront + WAF del doc 07 queda escrito en `infra/modules/edge/cloudfront.tf` detrás de `habilitar_cloudfront = false`, el mismo patrón de guarda que `prod` (D16): basta ponerlo en `true` y aplicar. **Acción pendiente para el operador: verificar la cuenta con AWS Support para habilitar CloudFront** (y con él, WAF y el hosting de los estáticos con OAC).
- **A-35** — La `URL_BASE` de payments (y el `return_url`/`cancel_url` que se envían a PayPal) apunta al borde HTTPS de A-34, no al ALB. _Motivo:_ PayPal rechaza URLs de retorno sin HTTPS, igual que el webhook.
- **A-36** — El worker de webhooks recibe por la cola **solo el `paypalEventId`**; el cuerpo crudo lo lee de `webhooks_paypal`. _Motivo:_ la bitácora se escribe antes de encolar y sobrevive a cualquier fallo posterior (doc 09 §4), así que es la fuente de verdad; mandar el payload por SQS lo duplicaría y chocaría con el límite de 256 KB del mensaje.
- **A-37** — El endpoint del webhook responde 200 también cuando el cuerpo no es JSON o no trae `id`. _Motivo:_ misma razón que con la firma inválida (doc 09 §3): cualquier respuesta distinta de 200 le confirma a quien sondea que su petición llegó a un endpoint vivo.

### F9 — web-app

- **A-38** — `output: 'standalone'` en `next.config.mjs` se activa solo con `SALIDA_STANDALONE=1`, que se pone únicamente dentro del Dockerfile. _Motivo:_ el modo standalone crea symlinks al copiar `node_modules`, y en Windows eso exige privilegios que una sesión normal no tiene (`EPERM: operation not permitted, symlink`): el `bun run build` local fallaba mientras que el de la imagen —que corre en Linux— funciona. La alternativa era pedirle al desarrollador que abra la terminal como administrador o active el Modo Desarrollador, es decir, un requisito de entorno para algo que solo importa al construir la imagen.
- **A-39** — El lint de convenciones acepta `process.env` también en `apps/*/src/lib/config.ts`, no solo en `infrastructure/config/`. _Motivo:_ la regla real (doc 12 §4) es que **un solo archivo** lea el entorno y el resto reciba valores ya validados; la app Next no es hexagonal y no tiene `infrastructure/config/`, pero su equivalente exacto es ese módulo. Se exceptúa la ruta concreta, no el patrón `config.ts` en general, para que la regla siga fallando si alguien lee el entorno desde un componente.
- **A-40** — La imagen del frontend construye `apps/web` como **proyecto aislado** (`bun install` sobre su propio `package.json`), no como workspace del monorepo. _Motivo:_ instalando el workspace completo, bun deja los binarios en su store (`node_modules/.bun/next@…/node_modules/next`) sin enlazarlos en `node_modules/.bin`, así que `bun run build` termina en `next: not found` (exit 127); `bunx next build` empeora la cosa descargando una versión distinta de Next. La app no importa nada del monorepo —solo su propio alias `@/`—, así que aislarla no cruza ninguna frontera ni duplica código compartido.
- **A-41** — El frontend habla con los servicios **siempre por el gateway** (`API_BASE`), nunca directo a un puerto de servicio, y en local ese gateway es el nginx de `tools/nginx.conf` que replica las listener rules del ALB. _Motivo:_ que las URLs sean idénticas en local y en AWS; si el frontend usara `http://catalog:3000` en local, un error de ruta solo aparecería al desplegar.
- **A-42** — La pantalla 7 vive en `/aprender/[cursoSlug]/evaluacion/[tomoId]`, no en `/aprender/[cursoSlug]/[tomoId]/evaluacion` como dice el doc 11 §2. _Motivo:_ el App Router de Next no admite dos segmentos dinámicos con nombre distinto en la misma posición (`[leccionId]` y `[tomoId]` son hermanos), y falla en arranque con `You cannot use different slug names for the same dynamic path`. Poner `evaluacion` como segmento estático antes del id resuelve el choque sin perder legibilidad de la URL; los ids son UUID, así que nunca colisionan con la palabra `evaluacion`.

### F10 — despliegue completo a dev

- **A-43** — El frontend atiende `/*` detrás del **mismo ALB**, con la prioridad más alta en número (100), y no CloudFront→S3 como dice el doc 07 §5. _Motivo:_ CloudFront sigue bloqueado (A-34) y el frontend es SSR, no estático (doc 11 §1), así que S3 tampoco lo serviría. Poniéndolo detrás del ALB con la regla más débil, todo lo que matchea `/api/…` sigue yendo a su servicio y solo lo demás llega al Next. No cambia ninguna URL: local y AWS siguen siendo idénticos (A-41).

- **A-46** — **La cuenta no tiene acceso a ningún modelo de Bedrock.** `InvokeModel` y `Converse` devuelven `ValidationException: Operation not allowed` incluso con `AdministratorAccess`, y `get-foundation-model-availability` da `authorizationStatus = NOT_AUTHORIZED` para todos los modelos de Anthropic (y `get-use-case-for-model-access` responde "You have not filled out the request form"). ### F12 — CI, aceptación y cierre

- **A-49** — El pipeline aplica el state de cada servicio en `services/<servicio>/infra`, no en `infra/envs/dev/services/<servicio>` como sugiere el ejemplo del doc 12 §8. _Motivo:_ el doc 06 §5.3 —que es el que manda sobre el layout— pone la infra de cada servicio **junto a su código**, y así quedó desde F4-bis. Un cambio de infra y el cambio de código que lo necesita viajan en el mismo commit y los ve el mismo path filter.
- **A-50** — El rol de CI (`edtech-dev-ci`) enumera acciones en vez de dar `*`, salvo tres casos donde la API de AWS no admite acotar por recurso: `ecr:GetAuthorizationToken`, las acciones `Describe*` de ELB/ECS/autoscaling y `xray:PutTraceSegments`. _Motivo:_ dejarlo escrito para que la próxima revisión no lo lea como descuido. La condición del `sub` de OIDC ata el rol a `repo:AnrrousUTP/edtech-solution:ref:refs/heads/main`: un fork no puede asumirlo.
- **A-51** — **La rotación de refresh no estaba activada.** El doc 08 §5 la pide ("refresh 30 días, con rotación de refresh token") y el cliente la tenía en `null`. Se activó (`feature = ENABLED`, gracia de 60 s) y eso obligó a quitar `ALLOW_REFRESH_TOKEN_AUTH` de `explicit_auth_flows`, porque Cognito prohíbe las dos cosas a la vez: con rotación, el refresh pasa por el **endpoint de token**, que es justo por donde lo hace el Route Handler del servidor (doc 08 §7). Verificado por el camino real: login PKCE del Hosted UI → el refresh devuelve uno nuevo → reutilizar el viejo da `400 invalid_grant`.
- **A-52** — Las `callback_urls` de Cognito ahora incluyen el borde HTTPS de `dev` además de `localhost:3000`. _Motivo:_ sin eso el Hosted UI rechaza el `redirect_uri` del frontend desplegado y el login solo funcionaba en local — un fallo que no aparece en ningún test y sí en el primer intento de entrar a `dev`.
- **A-53** — La federación con Google queda escrita detrás de `habilitar_google = false`, leyendo `edtech/dev/google-oidc` de Secrets Manager. _Motivo:_ las credenciales son de una app de Google Cloud del operador y no pueden salir de un `.tf` ni de un default (D17). Es la tercera guarda del mismo patrón, junto a `habilitar_cloudfront` (A-34) y `habilitar_bedrock` (A-46).
- **A-54** — El seed y el publicador de cursos abortan con `NODE_ENV=production` o `ENTORNO=prod` (R19). _Motivo:_ el riesgo está declarado en el doc 15 y la mitigación decía "el seed verifica `NODE_ENV`"; no lo verificaba. Ahora sí, y se comprobó ejecutándolo.

El resultado del checklist de cierre del doc 15 §3 está en [`CIERRE.md`](CIERRE.md), y se puede volver a correr con `bun run tools/verificar-cierre.ts`.

- **A-55** — La comprobación de I-12 **no** usa el grep literal del doc 15 (`git log -p | grep -iE "client_secret|AQ[A-Za-z0-9]{20,}"`), sino un detector propio en `tools/deteccion-secretos.ts` **con su propio test**. _Motivo:_ el grep literal devolvía 41 coincidencias sobre este repositorio y **ninguna era un secreto**: el nombre `PAYPAL_CLIENT_SECRET` en la documentación, los `sha512-…` del lockfile que contienen la subcadena `AQ`, y el propio texto del invariante citado en los docs. Con 41 falsos positivos, un positivo de verdad se pierde entre ellos y la comprobación deja de servir. El detector busca lo que sí sería una fuga —un **valor** con forma de credencial asignado a un nombre de secreto, o un token con forma de clave de PayPal/AWS— y excluye por lista los identificadores públicos que se le parecen (el alfabeto de `EDT-XXXX-XXXX` de A-29, los `AIDA…` del state de bootstrap).
  **Hallazgo del cambio:** la primera versión de la comprobación daba **verde sin mirar nada**, porque el pipe fallaba dentro de la shell de Bun y `Number('')` es `0`. Una comprobación de seguridad que nadie probó puede estar diciendo que sí sin haber leído una línea; por eso el detector tiene 9 tests, tres de ellos con secretos falsos que **debe** encontrar.
- **A-56** — El bloqueo de MFA del admin **no estaba implementado en el frontend**. La Lambda `pre_token_generation` marcaba el id token con `mfa_pendiente` (verificado contra Cognito real en F12), pero el callback no leía ese claim y las pantallas de `/admin` no lo miraban: un admin sin segundo factor entraba igual. El doc 08 §6 dice literalmente "el frontend lo manda a configurar MFA **antes de dejar entrar al panel**". Se agregó: el claim viaja a la cookie de perfil, las tres pantallas de admin lo comprueban, y `/configurar-mfa` guía el alta del TOTP.
  Las tres llamadas a Cognito (`AssociateSoftwareToken`, `VerifySoftwareToken`, `SetUserMFAPreference`) se hacen **por HTTPS directo, sin el SDK de AWS**: van firmadas con el access token del propio usuario, no con credenciales IAM, así que el SDK no aporta nada y sí pesa en una imagen que se construye aislada (A-40). Mismo criterio que con X-Ray en el kernel (A-45).
